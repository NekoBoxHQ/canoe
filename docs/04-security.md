# 04 · 安全模型

**先说实话：这一版模型下，客户端必然拿得到节点。**

订阅模式就是"把节点给客户"。客户端要连节点，就必须能解密订阅 ——
密钥在它手上，所以任何本地手段（dump 内存、反编译、抓包）都能把节点
扒出来。**这层加密防的不是拿客户端的用户。**

那它防什么、真正的边界在哪，是本文的全部内容。

---

## 0. 一句话结论

> 安全边界不在"客户端看不到节点"，而在**"服务端随时可以不给"**。

具体到三条：

1. **传输途中是密文。** HTTPS 之外再包一层 AES-256-GCM，密钥每次登录现发
   —— 反向代理的日志、链路中间环节、抓包工具都拿不到订阅正文。
2. **服务端完全可控。** 封禁 / 到期 / 取消绑定 → 服务端回**空信封**，
   客户端收到就地销毁本地订阅（内存里那几行）并断开。
3. **不落盘。** 订阅正文和 `sub_key` 都只在内存里 —— 关掉客户端就没了，
   下次必须重新登舟、重新验证身份、重新拉。

一个已经拿到节点的用户能做的，和普通机场一样：自己用、分享给别人。
**真正的兜底在服务端**（随时停发）和**节点服务器的防火墙**
（只接受你自己知道的来源），不在客户端。

---

## 1. 四层，逐层看

### 第 1 层：会话密钥层 —— 订阅在传输途中是密文

登录时服务端**当场生成**一把 32 字节的 `sub_key` 随登录响应下发，
只存在会话内存里（`tokens.sub_key`，客户端也只在内存里留一份）。

`/api/subscription` 回的不是链接明文，是一个信封：

```json
{
  "alg": "AES-256-GCM",
  "salt": "9f3K…",
  "nonce": "Q2x…",
  "data": "b8FI…",
  "revision": "3f9c1e0a2b7d4e51"
}
```

- 密钥：HKDF-SHA256(`sub_key`, salt) 派生，**每次响应新 salt、新 nonce**，
  所以同一条订阅两次拉取密文不同；
- 认证：`alg` 与 `revision` 作为 AAD 参与 GCM 认证 —— 有人篡改信封头
  （比如换个算法标识）解密就会失败；
- 换一把密钥解不开：冒烟测试里有对应断言。

这把钥匙和令牌同生命周期。令牌一吊销，服务端就再也取不到它，
客户端也就拉不到任何解得开的内容。

> ⚠️ 它防的是**传输链路**（反向代理、镜像、日志、公共 Wi-Fi），
> 不是本地。客户端必须能解密，密钥就在它手上。

### 第 2 层：类型层 —— 明文响应里根本没有装节点的字段

这是"服务端不会手滑"的保证，不是"客户端看不见"的保证。

`canoe-core/canoe_core/models.py` 里，客户端可见的响应类型**没有**
任何能装节点链接的字段：

```python
class ConfigResponse(BaseModel):
    protocol: int
    session_id: str
    node_name: str | None = None
    expires_at: int
    heartbeat_interval: int = 30
    revision: str = ""          # ← 指纹，只取哈希
```

节点只有一个入口：`SubscriptionResponse.envelope` —— 一个**密文**容器。
类型上就没有"顺手多加一个字段把明文带出去"的位置。

再加一道**可执行的断言**兜底（`canoe_core/links.py`）：

```python
find_leaks(payload)      # 递归扫描序列化结果，找出任何一处 "ss://" / "vless://" …
assert_no_leaks(payload) # 有就抛异常
```

每个客户端可见的明文响应出网前都过一遍 —— 扫到一行链接**直接 500**，
而不是静默泄漏。新加下发接口时照做。

### 第 3 层：可控层 —— 服务端随时可以不给

这是整套模型的**主承重墙**。

| 情况 | 服务端怎么做 | 客户端看到什么 |
|---|---|---|
| 账号被封 | 回空信封 + 吊销令牌 | 拉回来是空 → 销毁本地订阅 → 靠岸 |
| 账号到期 | 回空信封 | 同上 |
| 取消绑定 | 回空信封 + 定向推送 | 同上（在航的当场重拉） |
| 节点链接改了 | 新密文 + 定向推送 | 重新拉，拿到新链接 |

空信封 = `envelope.data == ""`。客户端见到它**必须**销毁本地订阅，
这是"服务端完全可控"的落点，`test_server.py` 里有一整节在盯这条。

心跳是第二条发现通道：每次心跳服务端都回当前 `revision`，
客户端比对发现变了就重拉 —— 即使推送那条长连接断了也跑不掉。

### 第 4 层：不落盘 —— 关掉就没了

`sub_key` 和订阅正文都只在内存里：不写配置文件、不写注册表、不提供导出。

`canoe-client/canoe_client/session.py` 是内存态；进程一退，
下次启动必须重新登舟 —— 也就是重新验证身份、重新拿密钥、重新拉订阅。
客户端上不存在一份"离线也能用的节点副本"。

## 2. 攻击面分析（诚实版）

假设用户是"恶意的付费用户"，我们分别看他能做什么、我们靠什么兜。

| 攻击 | 结果 |
|---|---|
| 抓包看传输 | 只看到 HTTPS + 一层 AES-GCM 密文，拿不到订阅正文 |
| 反编译 / dump 内存 | **能拿到节点** —— 客户端必须解密，这是模型的固有代价 |
| 用别人的令牌调接口 | 拿不到：令牌无签名泄漏，且校验设备 |
| 把节点分享出去 | 拦不住。兜底是**随时停发**（第 3 层）和节点防火墙（下节） |
| 直连节点服务器 | 拦不住 —— 所以节点那边要有防火墙，只放行你认识的来源 |
| 中间人劫持服务端流量 | 生产强制 HTTPS + HSTS；客户端 TLS 校验默认**开着** |

最后两行是关键：**既然拦不住用户直连节点，就得让节点只接受你允许的来源。**

### 节点服务器上必须补的一刀

```bash
# 在节点服务器上，只放行你自己的出口 IP / 中转机
ufw default deny incoming
ufw allow 22/tcp
ufw allow from <你自己用出口 IP> to any port <节点端口> proto tcp
ufw enable
```

**这一条在本项目的代码之外，但缺了它，第 3 层的实际价值会打折** ——
拿到链接的人可以绕过你的服务端直接连。把节点绑到固定来源上，
"分发"和"使用"就重新绑在一起了。

---

## 3. 为什么"服务端可控"比"客户端看不到"更实在

老模型（中转层）追求的是"客户端拿不到节点"，代价是：

- 服务端要**自己跑中转、承载全部用户流量** —— 一台机器被打就是全线瘫痪；
- 要维护 sing-box 配置渲染、热重载、端口编排、Nginx 按路径反代；
- 节点换了要重载中转层，出问题时排查链路长。

新模型把节点服务器摘出去之后，服务端只剩"发订阅"这一件事：
**它被打不影响已经拿到节点的用户继续用**，但反过来 —— 用户也脱离了控制。

所以这一版换了抓手：不追求"拿不到"，追求**"随时能收"**。
真正决定用户还能不能用的，是下一次登录 / 心跳 / 更新能不能拿到内容。

一个已经连上的用户，在服务端停发之后仍然能用到当前会话结束 ——
这是这个模型明确的、写在纸面上的边界。

## 4. 其它已实现的安全措施

| 项目 | 做法 |
|---|---|
| 密码存储 | PBKDF2-SHA256，24 万次迭代，**永不存明文** |
| 登录令牌 | 不透明随机串，库里只存 SHA-256；**不用 JWT**（要能立即吊销） |
| 封禁 | 立即吊销令牌 + 结束会话，不是"等它过期" |
| 管理接口 | `/api/admin/*` 每个请求二次校验 `role == admin`；前端隐藏入口不算防护 |
| 面板令牌 | 放 `sessionStorage`，不放 cookie —— 省掉 CSRF 面 |
| 令牌/订阅存储 | **仅内存**，退出即失效 |
| 传输 | 生产强制 HTTPS + HSTS |
| 登录限流 | 建议在 Nginx 上做（每 IP 10 次/分钟） |

### 为什么不用 JWT

1. **JWT 是无状态的，签发后无法撤销。** "管理员点了封禁，用户还能用到过期"
   对这类工具是致命的 —— 封禁必须立即生效。
2. 库里只存哈希，泄漏不等于账号沦陷。
3. 每次请求多一次索引查询，这个量级可以忽略。

### 为什么令牌、订阅都不落盘

宁可每次启动重新登舟，也不让任何凭证落到磁盘上。如果你要"记住我"，
正确做法是用 Windows 凭据管理器（DPAPI），而不是 `json.dump(token)`。

## 5. 自动化验证

约束不是纸面承诺，是可执行的断言：

```bash
# 服务端 93 项 —— 含「订阅响应里没有明文链接 / 域名」「解出来就是那行链接」
#              「取消绑定后回空信封」「明文响应里没有任何节点信息」
python canoe-server/smoke_test.py https://127.0.0.1:8443 --insecure

# 客户端 6 套 281 项 —— 含「订阅在传输中是密文」「空订阅就销毁」
#              与真服务端联调的 test_server.py 里有一整节在盯这条
cd canoe-client && python tests/test_server.py

# 面板 32 项 —— 含「面板不引用任何外部资源（无 CDN）」
cd canoe-server/panel && bun run test_panel.mjs
```

服务端测试里的核心断言：

```python
check("★ 响应里没有任何节点信息（节点只走加密订阅）", not scan_leaks(data))
check("★ 订阅响应里没有明文链接", "ss://" not in sub_body and "vless://" not in sub_body)
check("★ 订阅响应里没有节点域名", "leycc" not in sub_body)
check("★ 取消分配后回空信封（客户端据此销毁本地订阅）", not data)
```

客户端联调测试里的核心断言：

```python
check("★ 响应里没有订阅明文（域名）", "one.leycc.com" not in body)
check("★ 响应里只有密文信封", "envelope" in body and "data" in body)
check("★ 客户端解密后拿到两条链接", text == SUB_BOTH)
check("★ 换密钥解不开（密钥确实参与了加密）", True)
```

GUI 测试里另有一组：主界面没有"导出 / 查看配置"按钮，
界面上不出现协议 / 密码 / 端口字样。
